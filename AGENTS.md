# AGENTS.md

Guidance for coding agents working in this repository. Human contributors should start from
[`CONTRIBUTING.md`](CONTRIBUTING.md) and [`docs/handbook.md`](docs/handbook.md) (English
translation: [`docs/handbook.en.md`](docs/handbook.en.md)).

## Layout

- `rules/` — one rule per file (performance is measured per file). Platforms: `windows/`,
  `memory/`, `multi/`. New rules start from `rules/_TEMPLATE.yar`.
- `scripts/` — lint, fixtures, goodware scan, report/diff, bundles, coverage/health panels,
  hunt and memscan.
- `tests/` — pytest for the tooling, `cases.py` fixtures, `fakepe.py`, `samples.lock`. No real
  binaries in git. A local FP corpus lives under `tests/goodware/` (see that directory's README).
- `docs/` — `handbook.md` is the writing guide (Portuguese, the original; `handbook.en.md` is the
  English translation); `coverage.md` and `health.md` are generated, and CI fails if they are stale.
- `dataset.jsonl` — generated by `scripts/dataset_jsonl.py`, one JSON line per rule (path,
  platform, meta, string ids, test cases); CI fails if it is stale. Do not edit it by hand.
- `tools/anchors/` — extract decoder hex from samples into an `experimental` draft.
- `journal/` — historical build logs, not runbooks.
- `.github/workflows/` — `ci.yml` (PRs), `fp-watch.yml` (weekly), `release.yml` (semver tags,
  Sigstore/cosign keyless).
- `rules-ci.toml` — lint string floors and the time budget.

## Lint, tests, and CI locally

```bash
make setup-dev     # yara-x, ruff, mypy, pytest, bandit, yara-python, pre-commit
make lint          # compile + meta/lifecycle/uniqueness/string policies + yr fmt
make test          # synthetic positives and negatives
make quality       # ruff, ruff format, mypy, pytest, bandit
make ci            # lint + test + coverage-check + dataset-check + health-check + goodware + quality
```

`make ci` needs a local `tests/goodware/` tree for the FP gate. After changing a rule, increment
`version` and `modified`, then run `make fmt && make lint && make test && make coverage && make dataset && make health`
so the generated files stay in sync.

Other useful targets: `make fmt`, `make goodware GOODWARE=...`, `make report`, `make compat`,
`make bundles`, `make memscan IMAGE=...`, `make anchors SAMPLES='...' FAMILY=...`.

## Scope lint

`meta.scope` must be `file`, `memory`, or `both`. For `memory` or `both`, `scripts/lint_rules.py`
rejects condition clauses that only make sense on disk: `uintN(0)` (magic at offset 0),
`filesize`, and `pe.*`. `scripts/memscan.py` compiles only `memory`/`both` rules. A file rule
that checks MZ, filesize, or PE belongs in `scope = "file"`.

## Time budget

Set in `rules-ci.toml` and enforced by the CI report against the runner corpus:

- `max_rule_seconds = 20` — one rule scanning the whole corpus
- `max_regression_pct = 50` — versus the base branch, ignored below
  `regression_floor_seconds = 1.0` (runner noise)

Put cheap predicates first: magic, then filesize, then PE checks, then strings, then
regex/entropy.

## Do not `import "pe"` in hot rules

A YARA-X module parses every scanned file, before and independently of the condition.
`uint16(0) == 0x5A4D` written first short-circuits the condition, not the module. On the
Windows runner's PE corpus, `MAL_Win_Loader_FamilyX_ConfigMarker` with `import "pe"` took
28.14s (budget 20s). Since v3 the rule reads the two header facts by hand (`"PE\0\0"` at
`e_lfanew`, `NumberOfSections`) and the same corpus takes 0.32s. Use `pe.*` when you need
imports, version_info, or the rich header — not to ask "is this a PE?". See
`journal/2026-11-11-pe-budget.md` and `docs/handbook.md`.

## Common AI mistakes writing YARA-X

The compiler and [`docs/handbook.md`](docs/handbook.md) already caught these in the
example rule. They are frequent when a model writes YARA-X as if it were YARA 4.x.
Scan times below are the author's measurements on the Windows runner's PE corpus,
not a published benchmark.

### Unused strings are an error (`E022`)

YARA 4.x warned; YARA-X fails the compile. Do not leave `$fp_*` strings "for decoration".

```yara
// before — does not compile on YARA-X (E022)
strings:
  $marker = "CONFIG_START::mutex_id::"
  $fp_nsis = "NullsoftInst"  // never referenced
condition:
  $marker

// after
strings:
  $marker = "CONFIG_START::mutex_id::"
condition:
  $marker
```

### `pe.number_of_sections` → `pe.sections.len()`

```yara
// before — deprecated in YARA-X
import "pe"
condition:
  pe.number_of_sections < 12

// after — YARA-X only; pe.sections.len() does not exist in YARA 4.x
import "pe"
condition:
  pe.sections.len() < 12
```

This repo requires zero compiler warnings, so a deprecated field is not an option. If
the rule must also compile on YARA 4.x, do not use `pe.sections.len()`; read the header
by hand (next example). That is what `MAL_Win_Loader_FamilyX_ConfigMarker` v3 does.

### `import "pe"` is paid for every file

A YARA-X module parses every scanned file, before and independently of the condition.
Writing `uint16(0) == 0x5A4D` first short-circuits the condition, not the module. Use
`pe.*` when you need imports, version_info, or the rich header — not to ask "is this a
PE?". See [`docs/handbook.md`](docs/handbook.md) and
[`journal/2026-11-11-pe-budget.md`](journal/2026-11-11-pe-budget.md).

```yara
// before — 28.14s for one rule on the Windows runner's PE corpus (budget 20s)
import "pe"
condition:
  uint16(0) == 0x5A4D and
  filesize > 8KB and
  filesize < 2MB and
  pe.is_pe and
  pe.sections.len() < 12 and
  ($marker or $pdb or $ua or $decode) and
  2 of ($api_*)

// after — FamilyX v3 reads two header facts by hand; same corpus 0.32s;
// no engine = "yara-x" needed, and the rule compiles on YARA 4.x
condition:
  uint16(0) == 0x5A4D and
  filesize > 8KB and
  filesize < 2MB and
  uint32(uint32(0x3C)) == 0x00004550 and  // "PE\0\0" at e_lfanew
  uint16(uint32(0x3C) + 6) < 12 and       // FileHeader.NumberOfSections
  ($marker or $pdb or $ua or $decode) and
  2 of ($api_*)
```
