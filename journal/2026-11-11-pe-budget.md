# 2026-11-11 — the budget was right

With the UTF-8 fix (858acf2) the Windows job finally printed its whole report, and the report said
what the encoding crash had been hiding: `windows/MAL_Win_Loader_FamilyX_ConfigMarker.yar` took
28.14s over 39693 PE files (5.3GB). Budget: 20s. Every other rule: under 1s.

## Cause

`import "pe"`. A YARA-X module parses every file handed to the scanner, before and independently
of the condition. `uint16(0) == 0x5A4D and filesize ...` written first short-circuits the
condition, not the module. On the Linux ELF corpus the parser bails at byte 0 and nobody notices;
on System32 every file is a PE and gets the full parse. The strings and the hex stub were never
the problem.

Local reproduction (yara-x Python bindings, 47 PE files scanned 851 times = 39997 scans):

| rule | time |
|---|---:|
| v2 (`pe.is_pe`, `pe.sections.len() < 12`) | 16.8–17.6s |
| only `import "pe"` + `pe.is_pe` | 17.1s |
| v3 (header read by hand) | 0.42s |

## Change

v3 drops the import and reads the two facts it needed from the header: `"PE\0\0"` at `e_lfanew`
(`uint32(uint32(0x3C)) == 0x00004550`) and `FileHeader.NumberOfSections`
(`uint16(uint32(0x3C) + 6) < 12`). Same 25 fixtures, same verdicts (including
`familyx_strings_many_sections`); the two predicates agreed with the `pe` versions on 349 local
files (PE and ELF). Side effect: the rule now compiles on YARA 4.x, so `engine` went back to `any`.

The budget stays at 20s. It caught a real cost; raising it would have hidden the next one.

On the Windows runner after v3, the same corpus is 0.32s (was 28.14s). The 0.42s figure in the
table above is the local reproduction, not the runner number.
