## FP watch (`.github/workflows/fp-watch.yml`)

The question it answers: *did any stable/test rule start firing on clean software since the last
time we looked?* Weekly on Wednesday (Monday is `rules-ci`; two different days make "runner image
changed" and "rule changed" separable), plus `workflow_dispatch`.

- **Corpus**: the runner's own `/usr/bin`, `/usr/sbin`, `/usr/lib/x86_64-linux-gnu`, `/usr/libexec`,
  plus nine PyPI wheels pinned by version and sha256 in `tests/goodware/pip-corpus.txt`
  (cffi, charset_normalizer, cryptography, markupsafe, msgpack, psutil, pyyaml, regex, requests:
  native extensions with large `.so` files, the kind of goodware that catches a loose hex string).
  `pip download --require-hashes --only-binary=:all: --platform manylinux2014_x86_64` with the
  interpreter pinned, then unzip. A different hash means a different file, and then the download
  fails instead of silently scanning something the baseline never saw. Nothing is installed.
  `corpus_manifest.py` records every file's sha256 so runner drift is a diff, not a mystery.
- **Scan**: `scan_goodware.py --status stable,test` for the gate, `report.py --status stable,test`
  for hits with sha256 and time per rule. `--status` is new in both; `experimental` rules are
  allowed to be noisy and are not the watch's business.
- **Compare** (`fp_watch.py compare`): a hit whose sha256 is not in the rule's `known_fp` is new.
  New on `triage`/`blocking` → regression; new on `hunting` → warning. Time above
  `max_rule_seconds`, or more than `max_regression_pct` over the baseline above the noise floor →
  regression. Known FPs that vanished → informational ("corpus moved or rule tightened").
  The comparison is keyed by sha256, not path: the same `/usr/bin/foo` with a new build is a
  new FP, which is exactly the case the watch exists for.
- **Issue** (`fp_watch.py issue`): one open issue labeled `fp-regression` carrying an HTML marker.
  The body ends with a digest of the diff (run URL excluded). Same digest → zero write calls.
  Different → `PATCH` the body. Clean run with an open issue → one comment, close. Human-opened
  issues with the same label but no marker are left alone. Only `GITHUB_TOKEN`;
  `permissions: contents: read, issues: write`; `persist-credentials: false` on checkout.
- The job also fails on regression so the schedule shows red, but the issue is the deliverable:
  a red cron nobody reads is not an alert.

The baseline (`tests/goodware/baseline.json`) was generated here, on this VM, not on
`ubuntu-latest`: 0 known FPs for the one `test` rule, with this VM's corpus manifest hash. The first
CI run will say "corpus changed since baseline" (informational) and, if clean, nothing else.
Re-baselining from the run's artifact (`make fp-baseline REPORT=...`) pins it to the runner.

## Health panel (`docs/health.md`)

Coverage says what the repo *claims*; health says what it *costs and returns*. Per rule: status,
age, time since last change, known FPs, total FPs ever, last FP, last true match. The last two come
from two small data files: `baseline.json` (`last_fp`, `fp_total`, maintained by `fp_watch.py
baseline`) and `tests/activity.json` (`last_match`, written by the new `hunt.py --record-activity`
or by hand after an IR). Fixtures do not count as matches: a fixture is what the rule promises,
not what it delivered.

Deprecation candidate = has FP on record **and** no true match in 12 weeks (or ever). Not
automatic; it is a review agenda. There is also an "unproven" list: `test`/`stable` rules with
neither FP nor match. Today that list has one entry, the example rule, and that is the honest
state of a repo whose only family is fictional.

Ages are in bands (< 30 d, 30–90, 90–180, 180–365, > 1 year; "this week", "≤ 12 weeks",
"> 12 weeks") so the generated file is stable day to day, same trick as the coverage panel. The
CI runs `health.py --check` next to `coverage.py --check`.

`tests/test_health.py` (6): repo panel up to date, deterministic render, candidate logic (FP and
staleness both required), bands, `--check` ignores the reference date but fails on a band crossing
or a baseline change, `record_activity` idempotent per day.

## Not done, on purpose

- No Windows leg for the watch. `rules-ci` already scans `System32` weekly; duplicating it here
  would mean a second baseline per OS. If PE goodware FPs become the common case, the watch grows
  a matrix and `baseline.json` grows a per-OS key.
- The baseline is not auto-updated by the workflow. Accepting an FP is a human decision and a
  commit; the watch only reports.
- `memscan.py` does not record activity yet; memory hits in an IR are rarer and `activity.json`
  accepts manual entries.
