# 2026-11-09 — round 6: a real target

Round 5 left an honest gap in `docs/health.md`: every `test`/`stable` rule was "unproven", because
the only family in the repo was fictional. Round 6 closes part of that gap without breaking the
doctrine (no live malware, no secrets), and leaves the rest visible.

## EICAR: the fixture is the target

Why EICAR. It is the one detection target that is real, published, byte-exact, harmless and
universally recognised: a 68-byte ASCII string (a valid COM program that prints its own name)
that every antivirus flags by convention. Its sha256 is public
(`275a021bbfb6489e54d471899f7db9d1663fc695ec2fe2a2c4538aabf651fd0f`). A rule that matches it is
not matching a stand-in built by us; it is matching the thing itself. That is a different kind of
proof from a `fakepe` fixture, and the only kind this repo can offer without a sample.

Two rules, status `test`, purpose `triage`, new prefix `TEST_` (the lint's name regex gained it;
EICAR is neither malware nor a hypothesis):

- `TEST_Multi_EICAR_File`: `filesize <= 128 and $eicar at 0`, which is the specification. The
  string in the middle of a document, a `.yar`, an AV log, is not the test file and does not fire.
- `TEST_Multi_EICAR_InZip_Stored`: zip local header at 0, the EICAR bytes, and a **stored** member
  header (method 0, sizes 0x44/0x44) followed by the first 14 EICAR bytes within 64 bytes.
  Deflated zips are opaque to YARA-X (no inflate); that is a negative fixture and a documented
  limit, not a hidden one. "If YARA-X can handle that cleanly" — it can, for stored; it cannot,
  for deflate, and the rule says so.

The literal string is not in the repo. Not in the rule (hex), not in `tests/eicar.py` (hex), not
in a comment. I wrote it in a comment on the first pass; `test_eicar.py::
test_literal_eicar_string_never_appears_in_tracked_files` caught it before the first commit, which
is the test earning its keep on day one. The reason is practical: the Windows job checks the repo
out on `windows-latest`, and Defender quarantines any file containing the 68 bytes, which would
make the checkout itself fail in ways nobody would connect to a comment in a `.yar`. GitHub's own
scanning is less of a concern, but the test guards both.

YARA-X warns `text_as_hex` on a hex pattern that could be a text literal. Here the hex is the
point, so the lint gained one suppressible warning: `// allow-hex-as-text` on the same line, and
only for that code. `test_rules.py --dump` now warns that it writes the EICAR in clear.

`tests/activity.json` records both EICAR rules with source `published-target`, and the health
panel explains the source. It is not hunting; it is the only case where fixture and target are
the same bytes, and it is labelled as such rather than hidden under `manual`.

## WannaCry: a public family, from public reports only

Goal 2 said optional, and "skip if not clean". I did it, because WannaCry is the rare family
where the public record is exhaustive and the anchors are unique strings, not heuristics:

- kill-switch domain `iuqerfsodp9ifjaposdfjhgosurijfaewrwergwea` (MalwareTech, Talos, Microsoft)
- embedded-zip password `WNcry@2ol7` (Securelist, Talos)
- component names `mssecsvc2.0`, `WANACRY!`, `@WanaDecryptor@`, `tasksche.exe`, `*.wnry`
  (Securelist, Microsoft, CISA TA17-132A)

Condition: PE under 8 MB and (kill switch or zip password or 2 of the component names). The
negative fixtures are the FP cases this family is known for: an IOC list as text (no MZ), a single
component name in a PE (a cleanup tool), the strings in a 9 MB PE (an AV installer with embedded
signatures). Hashes (`ed01eb…` tasksche.exe, `24d004…` mssecsvc.exe) are the ones cited by Talos,
Securelist and CISA; each source is in the rule's `meta`.

Honest caveats, also in `samples.lock`: I could not confirm the two hashes on MalwareBazaar from
this VM (the API now requires a key for every query). `fetch_samples.py` verifies the sha256 of
whatever it downloads before scanning, so a wrong hash fails loudly instead of passing. And the
rule is still "unproven" in `docs/health.md` until someone runs `real-samples` with a key, which
is the correct state for a rule nobody here has pointed at a real binary.

The residual FP risk: security tooling that embeds these strings inside a PE (signature
databases, IR utilities). `purpose = triage`, not `blocking`, and the weekly watch will tell.

## Re-baselining from the runner, never auto-committed

`fp-watch` got a `workflow_dispatch` input `propose_baseline`. When true, the job writes
`baseline.proposed.json`, `health.proposed.md` and a `baseline.patch` (a `git diff --no-index`
rewritten to the repo path) into the artifact, and pastes the diff into the run summary. It does
not touch the branch, does not open a PR, does not need `contents: write`. Permissions stay
`contents: read, issues: write`.

The human side: `gh run download <id> -n fp-watch-<id> -D build/artifact` and
`make fp-propose ARTIFACT=build/artifact`. `fp_watch.py baseline --from-artifact` accepts the zip
or the extracted directory, finds `report.json` and `manifest.json`, rewrites
`tests/goodware/baseline.json` and `docs/health.md` in the working tree, prints `git diff --stat`
and stops. Zip-slip is rejected before extraction, like the pip corpus. Accepting an FP is still a
commit someone signs.

I considered having the workflow open the PR itself (`peter-evans/create-pull-request` or
`gh pr create`). It needs `contents: write` and `pull-requests: write` on a scheduled job, and
turns a human decision into a button someone clicks without reading. The patch in the artifact is
the same convenience with none of that.

## Baseline and panels

The local baseline was regenerated with the three new `test` rules (0 known FPs, 3350 files on
this VM's corpus). On the Linux corpus the PE-gated rules barely run: YARA-X short-circuits
`uint16(0) == 0x5A4D` before searching patterns, so WannaCry costs 2 ms over 786 MB. That is
correct and also means the Linux watch says little about PE rules; `rules-ci`'s Windows job on
`System32` is where those are exercised.

`docs/coverage.md`: 5 rules, 2 families + fictional, T1486/T1210/T1543.003 added, `none` for
EICAR with the panel's existing note that `none` is valid when there is no honest technique.
`docs/health.md`: EICAR rules show "this week / published-target"; FamilyX and WannaCry remain in
"unproven".

## Not done, on purpose

- No second public family. Candidates like Mirai or Emotet have dozens of variants and string sets
  that drift; one of them would be a hunting rule pretending to be triage. WannaCry is the
  exception because it stopped evolving in 2017 and the record is frozen.
- No deflate support for the zip rule. Inflating belongs to an unpacker in front of the scanner;
  a YARA rule that pretends to see inside compressed data is the wrong tool.
- No EICAR variants beyond the spec (no UTF-16, no base64 of the string). EICAR is defined as the
  ASCII bytes at offset 0; everything else is a different thing with a different name.
- The WannaCry hashes are not MalwareBazaar-confirmed from here. Stated in `samples.lock`; the job
  that uses them verifies sha256 before scanning.
- No automatic PR for the baseline. Stated above; the artifact patch is the deliberate stopping
  point.
- `fp-watch` still has no Windows leg. Unchanged from round 5.
